# Enterprise OIDC and SAML SSO

Release classification: first release, M4. Status: proposed; no enterprise provider is configured. Last reviewed: 2026-10-15.

[Documentation index](../README.md) · Prerequisites: [persistence](../03-database-and-persistence/README.md), [security](../04-security-and-audit-foundations/README.md), [authorization](../08-authorization-and-bootstrap/README.md), [MFA](../09-multi-factor-authentication/README.md), [Google/passkeys topology](../11-social-authentication-and-passkeys/README.md)

## Objective and scope

Accept enterprise OIDC authorization-code and SAML 2.0 SP-initiated sign-in through `@better-auth/sso`. The service is an OIDC relying party and SAML service provider. Becoming an OAuth/OIDC issuer, organizations/tenant realms, SCIM, automatic group-role provisioning, IdP-initiated login, and federation logout are outside release one. Both inbound protocols remain mandatory first-release features.

Only SuperAdmins with fresh assurance administer enterprise trust. A provider is explicitly enabled for approved applications; knowing its ID, domain, or email suffix grants no access. Enterprise identities join the existing shared user realm only through controlled immutable-identity binding and proof of the live external identity.

## Architecture and design

### Provider trust and identity resolution

Use native persisted SSO providers, native account linking/session creation, and native protocol validation. Disable organization provisioning and implicit signup. At the public sign-in boundary require an explicit `providerId` and `providerType`; reject domain/email/organization autodiscovery and `requestSignUp`, scope overrides, and arbitrary additional parameters. This avoids ambiguous provider choice and keeps app binding authoritative. Manually verified enterprise domain control is a provisioning prerequisite, not an email-suffix authorization rule.

Use the pinned plugin's supported `resolveUser` hook. It receives the cryptographically verified `accountKey` (`issuer`, `accountId`) and provider reference; OIDC includes verified ID-token claims, SAML includes signed identity/attributes. The hook runs inside the native transaction that finalizes accounts/sessions. Resolve only an exact existing native account for this boundary or an approved `identity.sso_identity_bindings` record for the immutable issuer/subject and existing user. Return `{action:"link",userId,profile:"preserve"}` for an approved first binding, `{action:"continue"}` for an already exact approved native binding, or `{action:"reject",code}` otherwise. Email equality and unverified profile fields never select an existing user. Recheck membership, account status and binding revocation through the shared service gate; deny if policy storage is unavailable. Do not set global roles or membership from OIDC claims, SAML groups, `provisionUser`, or email domains.

The administrator verifies the immutable subject with the enterprise through a trusted provisioning channel before approving the binding. Actual login still requires a validated assertion/token for that same subject. Changes in email do not alter the binding. Revoking a service binding blocks subsequent sign-ins and existing sessions tied to that provider through service policy, even if the native account remains for historical reconciliation. No administrator fabricates a successful protocol assertion.

### Host, callback, and browser binding

Use phase 02's exact allowlisted HTTPS dynamic base URL and authenticated ingress. Register `/api/auth/sso/callback/{providerId}` and SAML ACS `/api/auth/sso/saml2/sp/acs/{providerId}` for each application host enabled for that provider. Register matching SP entity ID/audience and exact destinations; providers that cannot support the chosen multi-app metadata/configuration must use distinct provider registrations per application, never weaken audience/destination checks. The approved public origin is selected from authenticated application context, not forwarded input from the browser.

Bind OAuth state or SAML AuthnRequest/RelayState references, provider, application, browser context and callbacks through `identity.auth_flow_bindings`. Store HMAC references, not copied protocol tokens. Verify the callback against the initiating application even if all apps are globally trusted origins. The native provider-reference fingerprint fences in-flight authentication against changes to provider trust; do not persist that transient fingerprint as a user/tenant identifier.

SAML requires an explicit browser correlation defense: v1.7.8 `parseRelayState` deliberately skips its state-cookie check for cross-site POST because Lax cookies are absent. Native request correlation alone therefore does not establish the initiating browser. Have the BFF issue a separate short-lived, host-only, Secure, HttpOnly, `SameSite=None` correlation cookie at initiation. Before releasing the native `{url,redirect}` result and cookie, extract the opaque native RelayState from that approved returned SAML authorization URL; store its HMAC reference with the cookie's keyed HMAC, provider, application/origin, and five-minute expiry in the same trusted initiation context. No SAMLRequest XML decoding or undocumented request-ID callback is needed. At POST ACS, locate the binding by RelayState HMAC, verify the browser cookie/application and atomically consume the service binding before forwarding; native InResponseTo independently validates the actual AuthnRequest. This cookie is not a sign-in credential and cannot authorize a user. Keep session cookies Lax. Missing/blocked/expired correlation fails closed with a safe restart; do not disable correlation to accommodate a browser. Never log its value. Retain native state and InResponseTo validation as independent checks.

### OIDC and SAML policy

OIDC uses PKCE, state and native ID-token signature/issuer/audience/nonce/expiry validation. Require `openid email profile` only, exact configured issuer and trusted discovery/JWKS/token endpoints, and no OIDC IdP-initiated flow. Prefer `private_key_jwt` with the supported `resolvePrivateKey` callback backed by a secret manager; support encrypted client-secret configuration where required. Rotate JWKS through issuer-pinned validation, not arbitrary token-supplied URLs.

SAML sets `wantAssertionsSigned: true`, `saml.enableInResponseToValidation: true`, `allowIdpInitiated: false`, `requestTTL: 300000`, `clockSkew: 60000`, `requireTimestamps: true`, `algorithms.onDeprecated: "reject"`, and `maxResponseSize: 262144`. Configure signed AuthnRequests and encrypted-at-rest SP signing material where the IdP supports/requires them. Validate trusted IdP entity ID/certificate, signature coverage of the consumed assertion, NameID, audience, recipient/destination, time conditions, provider reference, RelayState and InResponseTo. Accept only maintained XML parsing/signature code; no custom XML extraction, unsigned-assertion fallback, SHA-1 compatibility switch, or external-entity expansion.

Native InResponseTo records fall back to the shared `auth` verification table when secondary storage is absent. Preserve atomic native consumption/replay handling; no in-memory replay map is acceptable across instances. A successful IdP factor claim, `acr`/`amr`, or passkey at the IdP does not replace the enrolled local TOTP/recovery factor. Every resulting session enters the same service assurance gate.

## Dependencies and prerequisites

Enterprise OIDC and SAML authentication must work for both web and native iOS/Android in release one. Native clients run federation and required local MFA in the registered mobile HTTPS portal's system browser, including the existing SAML correlation cookie. Provider callbacks remain on that registered HTTPS host, followed only by the guarded [mobile handoff](../14-mobile-authentication/README.md) to the verified app link. Do not register arbitrary device schemes as enterprise ACS/OIDC callbacks or expose native service secrets to the device.

Complete M1–M3, pin compatible Better Auth/SSO packages, and establish privileged bootstrap, application membership, fail-closed policy hooks, audit, SMTP security notifications and the secret manager. Provider onboarding requires verified issuer/entity ID, enterprise contact, allowed applications, immutable subject format, callback registration, signing certificates/rotation plan and bounded metadata. These are required inputs, not fabricated deployment facts.

Discovery/metadata fetching uses an outbound SSRF boundary: HTTPS allowlist, DNS resolution and connected-IP checks, blocked private/link-local/loopback/metadata-service ranges, bounded time/size, and revalidation on redirects/DNS changes. Disable unreviewed redirects. An enterprise requiring private-network IdP access needs an explicit operator-managed egress exception restricted to exact targets; a SuperAdmin-supplied URL alone does not grant it. The native discovery helper does not replace this network policy.

## Database design

- `auth`: native SSO provider, account, user, session and verification tables. Preserve native fields/IDs, foreign keys, row locking, transaction support, uniqueness and protocol-specific verification records. No TypeORM mirrors or base-entity inheritance.
- `identity.sso_provider_applications`: native provider identifier, application ID, `enabled` boolean, custom UUID/version/timestamps; unique provider/application. There is no separate independently mutable status column. Disabling a mapping denies future and existing provider-derived access for that app.
- `identity.sso_identity_bindings`: custom UUID, provider identifier, exact verified issuer and immutable subject, native user ID, active/revoked status, approver, version/timestamps; unique provider/issuer/subject. Prevent the same external identity from binding to different users. Store no assertion or provider token.
- `identity.sso_provider_policies`: native provider identifier PK, status (`provisioning|active|disabled|failed`), version/timestamps, and safe last-operation reference. This owns provider administration ETags and fail-closed orchestration state. Reuse `identity.admin_operations` for durable operation intent/phases; do not add another workflow table.
- Reuse flow bindings and session assurance. Session policy context records provider ID and relevant binding/mapping version so disabled trust is rechecked authoritatively. Use `audit` for redacted administrative intent/outcome and protocol results.

### Secret protection and transactional boundaries

Do not assume `account.encryptOAuthTokens` encrypts SSO provider configuration. v1.7.8 registration serializes `oidcConfig` and `samlConfig` to plain JSON strings; these can contain client secrets and SP private keys. Add a narrowly scoped field-protection decorator around the supported PostgreSQL native adapter. Encrypt only these two native-model fields on create/update with authenticated envelope encryption and a versioned external key ID; decrypt them before plugin reads/returned rows, including transaction-bound adapters and joined/read/list results. Bind ciphertext to model, field and immutable native provider identifier, which is available before provider creation. Re-encryption updates ciphertext without changing plaintext authentication meaning. Fail closed on unknown keys/corruption. Preserve every other adapter operation, transaction, row lock, predicate, conditional mutation and atomic consume behavior. No custom credential store or community TypeORM adapter is introduced.

The supported exported `getAdapter` from `better-auth/db/adapter` asynchronously creates the standard PostgreSQL adapter from the complete auth options plus the native `pg.Pool`. During the async Nest provider initialization, construct it once, decorate it, and pass a synchronous `database` factory returning that prepared decorated adapter to Better Auth. Do not recursively call `getAdapter` with the decorated factory. Preserve `transaction(callback)` by wrapping the actual transaction adapter supplied to that callback, not by rerunning operations on the outer pool. Preserve adapter ID, options, capability metadata, property descriptors and symbol-keyed behavior so native transaction/locking checks remain intact. Core adapter transforms are factory-level capabilities, not a fictitious `sso.encryptConfig` option. Gate launch on typing, round-trip/transaction/rotation evidence; failure blocks the feature rather than enabling plaintext or another persistence path. Never query encrypted JSON fields for provider resolution; use native provider ID/issuer/domain columns. Keep encryption keys in the secret manager; prefer the exact native `resolvePrivateKey` callback when it avoids private-key persistence. Backups contain ciphertext, and operator views return only redacted configuration plus `secretConfigured` flags.

Native provider management retains its own transaction. Custom application/identity bindings use TypeORM and cannot share that transaction implicitly. Administrative orchestration first writes durable intent and disables affected mapping(s), invokes the native server API, then completes reviewed mapping/binding state; any partial failure keeps access disabled and exposes an operation ID for repair. Idempotency prevents duplicate creates. Fail closed while reconciling. The native provider owner is a designated bootstrap SuperAdmin; trusted server-side orchestration uses that owner's native context after separately authorizing the actual SuperAdmin and records both identities. Never impersonate the owner via a caller-controlled header or browser-accessible bypass.

## API contracts

### Native sign-in surface

These verified v1.7.8 paths are prefixed with `/api/auth`; native bodies, redirect errors, cookies and status codes remain native. Authenticated ingress establishes the application even for anonymous users; IdP callbacks use the protocol-specific ingress path and validated flow binding. Do not apply ordinary browser Origin rejection to a valid SAML POST or broaden the bypass to unrelated endpoints.

| Method and path | Request / caller | Result and effects | Errors and audit |
| --- | --- | --- | --- |
| `POST /sign-in/sso` | `providerId`, `providerType: oidc|saml`, approved `callbackURL`; optional approved `errorCallbackURL`, `newUserCallbackURL`, bounded `loginHint`. Native also accepts email/domain/organization/scopes/signup/additional parameters; service rejects those overrides. Provider/application must be enabled. | `200 {url,redirect:true}`; creates native OIDC state/PKCE or SAML AuthnRequest/RelayState, application/browser binding, and correlation cookie where needed. | Native invalid-provider/configuration and validation errors; service app denial/throttle. Audit `sso.started` with protocol/provider/app. |
| `GET /sso/callback/:providerId` | OIDC query `code`, `state`, optional provider `error`, `error_description`; native state plus application/provider binding. | Native redirect and session cookies after token validation and `resolveUser`; creates/links native account and session; service initializes pending assurance. | Invalid state, issuer/token/subject/provider-reference/link errors; approved error redirects. Audit `sso.failed` or primary success, no code/token/claims dump. |
| `POST /sso/saml2/sp/acs/:providerId` | Bounded form `SAMLResponse`, optional `RelayState`; trusted IdP protocol POST plus browser/request/provider/application correlation. | Native redirect and cookies after validated assertion and resolver; consumes native request/replay state and creates session; service initializes pending assurance. | Missing response `400`, missing provider `404`; native SAML validation errors commonly redirect with safe error query. Audit failed reason class or primary success, never XML. |
| `GET /sso/saml2/sp/acs/:providerId` | Native completion route: optional `RelayState`, existing usable native session and matching app/flow. This is not a GET assertion-submission route. | Native safe redirect; no new assertion acceptance. Service still enforces matching app and pending-session policy on destination. | Missing session gives native `invalid_request` error redirect; cross-app context denied. Audit `sso.callback_completed` or failure. |
| `GET /sso/saml2/sp/metadata` | Query `providerId`; approved provider/application host. Public metadata may be served through its approved BFF with read limits. | `200` native XML metadata; no session creation or secrets. | Native provider missing `404`, custom inactive mapping denial. Audit configuration access without XML contents. |

Block public native `POST /sso/register`, `GET /sso/providers`, `GET /sso/get-provider`, `POST /sso/update-provider` and `POST /sso/delete-provider`. They are server-orchestrated only; native ownership checks alone are insufficient service administration policy. Leave `options.redirectURI` unset and block unused shared `GET /sso/callback`. Disable domain-verification HTTP administration when manual domain approval is used. Disable `saml.enableSingleLogout`, block `GET|POST /sso/saml2/sp/slo/:providerId` and `POST /sso/saml2/logout/:providerId`. Local sign-out revokes the local session only and never promises to end the IdP session.

### Proposed Nest administration surface

All routes below are new service contracts under `/api/v1/admin/sso-providers`. Require a current SuperAdmin, active admin-application membership, fresh local factor assurance, CSRF protection, and authenticated BFF. Mutations require a durable redacted audit intent. Use phase 02 envelopes, pagination and ETags; PATCH/DELETE require `If-Match` (`428` absent, `412` stale). POST requires an `Idempotency-Key`. The actual actor and operation ID are mandatory audit fields. No raw secret/assertion is returned.

`ProviderView` contains `providerId`, protocol, issuer, domain, enabled application IDs, status (`provisioning|active|disabled|failed`), redacted endpoint/configuration fields, certificate fingerprints/expiry, `secretConfigured` flags, and version. Custom orchestration metadata is service-owned; native configuration stays in the native table. Administrative input selects one typed protocol configuration: OIDC client ID/authentication method, secret reference or write-only secret, PKCE and approved discovery/endpoints; or SAML entity/entrypoint/audience, trusted certs, bounded metadata and write-only SP key material. Server fixes security options and derives allowed callbacks from applications; unknown/unsafe fields fail validation.

| Proposed method and suffix | Request | Success / side effects / audit |
| --- | --- | --- |
| `POST /` | `providerId`, `protocol`, `issuer`, `domain`, typed configuration, `applicationIds`; verified enterprise/domain evidence reference. | `201` with `{operationId,provider:ProviderView}` only when native create and mappings complete; partial failure stays disabled and returns `503` with operation ID. Audit `sso.provider_created` intent/outcome. |
| `GET /` | `limit`, `cursor`; optional bounded protocol/status filter. | `200` page of ProviderView; audit `sso.providers_listed`. |
| `GET /:providerId` | Path ID. | `200` ProviderView plus ETag; audit `sso.provider_read`. |
| `PATCH /:providerId` | Allowlisted config/secret rotation proposal plus reason/evidence; ETag. | `200` ProviderView after guarded native update and mapping reconciliation. Audit `sso.provider_updated`; sensitive trust changes use the migration procedure below. |
| `DELETE /:providerId` | ETag and reason; mappings must first be disabled and dependent identity links reviewed. | `204` only after permitted native deletion/reconciliation. Refuse linked identities requiring a migration; audit `sso.provider_deleted`. |
| `PUT /:providerId/applications/:applicationId` | `{enabled:boolean}`, mapping ETag for existing row; new association uses `If-None-Match:*`. | `200` mapping `{providerId,applicationId,enabled,version}` or `201` new mapping; disabling immediately denies affected access and queues native-session revocation. Audit `sso.application_binding_changed`. |
| `POST /:providerId/identity-bindings` | `{issuer,subject,userId,evidenceReference}`; existing verified user, exact provider issuer, enterprise-approved immutable subject. | `201` `{id,providerId,issuer,subject,userId,status,version}`; no native account is linked until live proof succeeds. Audit `sso.identity_binding_approved`. |
| `DELETE /:providerId/identity-bindings/:bindingId` | ETag and reason. | `204`; mark binding revoked, advance security epoch/deny and revoke affected sessions; retain necessary audit linkage. Audit `sso.identity_binding_revoked`. |

Common custom errors: `400` invalid configuration/unsafe destination, `401` invalid session/caller, `403` insufficient permission/assurance, `404` missing resource, `409` duplicate identity/provider or forbidden trust-boundary mutation, `412/428` concurrency requirements, `429` abuse limit, `503` required native/policy/encryption/audit dependency unavailable. Return safe errors plus operation ID when reconciliation is needed. Never expose another user's bindings through regular sign-in errors. ETags for provider views derive from a service orchestration version, not an invented native version column.

## Security considerations

Configure native `guardProviderMutation`: it receives a locked provider and `isAuthenticationBoundaryChange` for updates, or delete action. Reject boundary changes by default, and reject destructive deletion with linked identities. The hook also protects trusted server API calls; public-handler blocking is not sufficient. Certificate changes affect authentication authority even if issuer stays unchanged.

Changing issuer/entity ID, subject interpretation, destination, client identity, or trust anchor cannot silently reuse existing account bindings. Use a new provider registration plus an explicitly reviewed identity migration with mappings disabled, old sessions revoked, immutable subjects verified and rollback prepared. A planned certificate rollover requires an explicit privileged operation context authorizing the exact old/new certificate fingerprints, bounded overlap and expiry, native validation, and invalidation of old in-flight flows; it is not a blanket `allowBoundaryChanges` flag. Preserve issuer/subject meaning throughout. Notify affected administrators through SMTP after trust changes.

Audit all provider mutations, binding approvals/revocations and federation results with app/provider IDs, protocol, safe outcome, actor/request/operation IDs and certificate fingerprints where relevant. Do not retain raw SAML/OIDC payloads, secrets or native token URLs. Pin XML/parser/signature dependencies and enforce size/decompression bounds at ingress before parsing. Support operational certificate-expiry alerts, discovery failures, replay signals and provider disablement without opening alternate login bypasses.

## Implementation plan

1. Configure the pinned plugin and explicit protocol policies; review native migrations, shared request/replay consumption and native transaction/row-lock capabilities.
2. Implement and verify SSO configuration field protection plus secret-manager key resolution/rotation before accepting any provider secret.
3. Implement service provider/app/identity metadata and durable administrative operation tracking using the existing TypeORM migration/policy conventions.
4. Expose guarded custom administration, block raw native management externally and authorize in-process native API orchestration through a nonserializable context; add `guardProviderMutation` and fail-closed reconciliation.
5. Implement exact-subject `resolveUser`, native account proof, per-app initiation/callback fences and browser correlation. Register per-host IdP callbacks/metadata without relaxing RP/audience checks.
6. Apply SSRF/egress, signature/time/replay, abuse/audit, membership and all-method assurance controls. Keep optional native routes/SLO disabled.
7. Collect OIDC/SAML interoperability, trust rotation, multi-instance replay and administrative failure evidence before M4 promotion. Validate operational alerts and provider kill-switch again at M5.

## Acceptance criteria

- SSO-01: Approved OIDC and SAML providers authenticate existing approved identities through each enabled application; unknown/disabled provider/application combinations and unauthorized provider administration fail.
- SSO-02: OIDC rejects invalid state/PKCE/nonce, signature, issuer, audience, expiry, endpoint substitution and wrong immutable subject; no email-only linking or implicit signup occurs.
- SSO-03: SAML rejects unsigned/incorrectly signed assertions, wrong entity/audience/recipient/destination, missing/expired timestamps, deprecated algorithms, unsolicited responses and malformed/oversized XML.
- SSO-04: Native AuthnRequest/RelayState and custom browser/application correlation survive multi-instance routing; replay/concurrent redemption produces at most one usable session. Missing SameSite=None correlation cookie fails safely.
- SSO-05: Provider tokens/configuration secrets and SP keys are encrypted or secret-manager-resolved, excluded from all views/logs, and rotate with working transaction/round-trip/restore evidence. Unknown encryption keys deny access.
- SSO-06: Provider claim/group/domain changes cannot grant roles/membership or silently rebind an identity. Controlled subject approvals require live external proof; revocation immediately denies affected access.
- SSO-07: Boundary mutation hooks reject silent issuer/entity/certificate rebinds. Explicit rollover/migration fences in-flight flows, revokes affected sessions and produces attributable audit evidence; partial operations stay disabled.
- SSO-08: SSRF/DNS/redirect/private-IP attempts, callback host swaps and cross-app flow/metadata swaps fail. Raw management/shared callbacks, IdP-initiated login and SLO remain unavailable.
- SSO-09: Every SSO primary session for an MFA-enabled user is denied protected native/Nest access until local TOTP/recovery succeeds; IdP MFA claims are insufficient. Local logout is documented and verified without implying IdP logout.
